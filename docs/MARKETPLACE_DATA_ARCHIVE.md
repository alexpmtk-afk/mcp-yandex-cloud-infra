# Marketplaces Archive Data Layer

Статус: CANONICAL

## Главный принцип

Архив маркетплейсов — это не один отчёт и не один CSV. Это единая логическая база, состоящая из нескольких независимых наборов данных.

Ни один отдельный отчёт Wildberries или Ozon нельзя считать полной картиной бизнеса.

Первый реализованный набор данных — `wb_weekly_finance_main`: еженедельный финансовый отчёт Wildberries, `reportType=1` (`Основной`). Он является только первым слоем архива.

Он не должен использоваться как источник истины для:

- заказов покупателей;
- ежедневной истории заказов;
- остатков товара на каждую дату;
- рекламных кампаний и затрат на продвижение;
- воронки продаж и конверсии.

Для этих задач создаются отдельные наборы данных.

## Историческая глубина

Первый полный backfill выполняется за 2026 год.

После стабилизации система должна быть углублена до 2024 года включительно там, где официальные API маркетплейсов позволяют получить такую историю.

Более ранняя история пока не входит в целевой обязательный объём проекта.

## Wildberries: план наборов данных

### `wb_weekly_finance_main`

Статус: реализован как первый архивный dataset.

Назначение: финансовая реализация и строки основного еженедельного отчёта WB.

Не заменяет заказы, остатки, рекламу или воронку.

### `wb_orders_daily`

Статус: запланирован.

Назначение: события заказов по датам и товарам. Именно этот dataset должен отвечать на вопросы вида «сколько единиц товара заказали за период».

### `wb_stock_snapshots_daily`

Статус: запланирован.

Назначение: исторические снимки остатков по датам, товарам и складам. Именно этот dataset должен отвечать на вопросы об остатке на конкретную дату и динамике запасов.

### `wb_promotion`

Статус: запланирован.

Назначение: данные продвижения и рекламных кампаний, расходы и доступные показатели эффективности.

### `wb_sales_funnel`

Статус: запланирован.

Назначение: воронка продаж и показатели конверсии, которые предоставляет официальный API.

## Ozon: обязательное расширение архива

Архив не ограничивается Wildberries. Для Ozon должна быть построена параллельная система наборов данных.

Предварительно выделены:

- `ozon_finance` — финансовые начисления и реализация;
- `ozon_orders_daily` — заказы и связанные события;
- `ozon_stock_snapshots_daily` — история остатков;
- `ozon_promotion` — Ozon Performance и продвижение;
- `ozon_sales_funnel` — воронка и конверсия.

Перед фактическим архивированием каждого Ozon dataset должен быть утверждён его точный официальный endpoint/report, схема полей, временная семантика и правила дедупликации.

## Data Routing Layer

Любой аналитический запрос должен проходить следующий путь:

```text
Запрос пользователя
        |
        v
Интерпретация бизнес-метрики
        |
        v
Canonical Data Catalog
        |
        v
Выбор marketplace + dataset + источника
        |
        v
Проверка покрытия периода архивом
        |
        +--> покрыто --> чтение архива
        |
        +--> не покрыто --> соответствующий официальный API / backfill / явный gap
        |
        v
Расчёт бизнес-метрики
        |
        v
Ответ с указанием использованного dataset/source
```

## Критическое различие бизнес-метрик

Слово «продажи» само по себе неоднозначно.

Оно может означать, например:

- заказанные покупателями единицы;
- финансово реализованные/выкупленные единицы;
- денежную реализацию;
- отгруженные товары.

Поэтому generic-запрос «продажи за год» нельзя автоматически считать запросом к финансовому weekly-отчёту. Сначала должна быть определена бизнес-семантика.

Примеры маршрутизации:

```text
«сколько единиц заказали»
    -> ordered_units
    -> wb_orders_daily / ozon_orders_daily

«остаток товара на 15 июня»
    -> stock_on_date
    -> wb_stock_snapshots_daily / ozon_stock_snapshots_daily

«расходы на рекламу»
    -> ad_spend
    -> wb_promotion / ozon_promotion

«воронка продаж»
    -> sales_funnel
    -> wb_sales_funnel / ozon_sales_funnel

«финансовая реализация WB»
    -> financial_realization
    -> wb_weekly_finance_main
```

## Контракт каждого dataset

Перед добавлением нового набора данных обязательно фиксируются:

1. marketplace;
2. бизнес-метрики, для которых он является правильным источником;
3. официальный API endpoint/report;
4. единица строки/grain;
5. временная семантика;
6. список/политика полей и колонок;
7. ключ уникальности и дедупликация;
8. путь хранения;
9. историческое покрытие;
10. статус архивирования;
11. политика обновления и повторного backfill.

## Машинный источник истины

Канонический машиночитаемый каталог находится в `app/core/data_catalog.py`.

MCP публикует два инструмента:

- `marketplace_data_catalog` — показывает datasets, покрытие и ограничения;
- `marketplace_metric_route` — переводит бизнес-метрику в правильный dataset.

`marketplace_system_map` фиксирует обязательность этого слоя на уровне общей архитектуры MCP.

## Хранилище

Каноническим хранилищем данных архива является **Google Drive**, корневая папка `MCP архив базы данных`.

На Google Drive находятся и являются source of truth:

- годовые CSV каждого dataset/cabinet/year;
- `app/registry/reports_registry.csv`, по которому определяется, какие отчёты уже полностью приняты.

Правило записи: сначала успешно обновляется Google Drive, затем те же байты сохраняются в Yandex Object Storage как резервная копия. Если запись в Google Drive не удалась, отчёт не должен считаться завершённым.

Yandex Object Storage остаётся обязательной частью runtime, но его роль другая:

- постоянное состояние очередей/backfill jobs;
- временный staging страниц больших отчётов;
- резервная byte-for-byte копия канонических CSV и registry.

При переходе со старой архитектуры действует read-through migration: если канонического файла ещё нет на Google Drive, но он уже накоплен в Yandex Object Storage, сервер копирует существующий файл на Drive при первом обращении. Повторно скачивать те же отчёты из WB/Ozon для этой миграции не требуется.

Доступ серверного MCP к Google Drive выполняется через владельческий Google Apps Script web-app bridge, который работает от имени владельца папки `MCP архив базы данных`. Общий секрет bridge хранится в Yandex Lockbox. Google Cloud OAuth refresh token больше не является runtime-зависимостью; Google Cloud как отдельная runtime-инфраструктура не используется.

## Дедупликация

Для `wb_weekly_finance_main` годовой CSV объединяется с дедупликацией по `(reportId, rrdId)`.

Реестр дедуплицируется по `(cabinet, dataset, report_id)`. Повторный запуск не должен повторно добавлять уже полностью принятый reportId.

## Durable Archive Queue

Исторический backfill не должен выполняться как один длинный MCP-запрос.

Канонический контракт очереди:

1. `marketplace_archive_update` принимает задание и сохраняет его состояние в Yandex Object Storage;
2. очередь ближайших к выполнению шагов хранится в shared Redis/Valkey;
3. один `marketplace_archive_worker_step` выполняет не более одного реального запроса к API маркетплейса;
4. каждый запрос по-прежнему проходит через общий `MarketplaceClient`, который определяет владельца квоты, endpoint и применимый rate-limit;
5. если лимит занят, HTTP-запрос к маркетплейсу не отправляется: job получает `WAITING_RATE_LIMIT`, сохраняется и переносится на время `retry_after`;
6. ожидание никогда не выполняется через `sleep` внутри MCP-соединения;
7. при сетевой ошибке или перезапуске worker продолжает задание с сохранённого курсора;
8. страницы большого отчёта сначала складываются во временный staging в Object Storage; только полностью полученный отчёт объединяется с каноническим годовым CSV на Google Drive и помечается `COMPLETE` в реестре;
9. повторный запуск не должен дублировать строки благодаря реестру reportId и вторичной дедупликации `(reportId, rrdId)`.

Таким образом, срок выполнения backfill может быть длинным, но отдельные MCP-вызовы остаются короткими и не зависят от времени ожидания квоты.

## Правило пограничной недели

Год архива определяется не жёстким обрезанием строк по 1 января и 31 декабря, а полными недельными отчётами, пересекающими целевой год.

Если недельный отчёт пересекает хотя бы один день 2026 года, он архивируется целиком. Для 2026 года поиск начинается с понедельника **29.12.2025**, потому что эта неделя содержит 01.01.2026.

Это правило действует и для последней недели года: если отчёт начинается в декабре 2026 года и заканчивается уже в январе 2027 года, после появления полного отчёта он относится к покрытию 2026 года целиком.
